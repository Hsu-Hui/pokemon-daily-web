## Context

目前 `getData()` 把抓取到的田野調查與可追蹤任務、使用者手動任務一起放在 `tasks`。前端 `derive()` 對所有群組建立勾選狀態、完成度與總覽提醒；`field-` 群組是唯一被設定為各項獨立勾選的類型。每次任務勾選、刪除或非同步回應都會重建 `main` 內容，瀏覽器可能失去原本的捲動位置。手動任務目前只有 `addManualTask` 與 `deleteManualTask`，無法原地修正。

此變更橫跨前端渲染、Apps Script UserProperties 與完成狀態清理，但不改爬蟲輸出、試算表結構或部署方式。

## Goals / Non-Goals

**Goals:**

- 將 `field-` 田野調查資料呈現為沒有勾選框的獎勵參考區。
- 讓其餘可追蹤任務組一致採用依序勾選。
- 讓手動任務可以安全編輯，並維持可對應項目的完成紀錄。
- 任務頁的局部操作與非同步回應不得把使用者帶回頁首。
- 讓儲存控制緊鄰任務頁標題，總覽只提醒真正未完成的任務組。

**Non-Goals:**

- 不讓使用者編輯爬蟲或試算表來源的任務組。
- 不新增田野調查來源、不改翻譯規則，也不更改每日抓取排程。
- 不把日常田野調查獎勵加入 Discord 提醒、任務進度或封存。
- 不新增跨帳號共享、歷史版本或復原已刪除手動任務的功能。

## Decisions

### 將田野調查獎勵與可追蹤任務分流

前端以群組 id 的 `field-` 前綴辨識現有 ScrapedDuck 田野調查資料。`derive()` 將它們整理為 `fieldRewards`，未結束者顯示在任務待辦的獨立參考區；它們不進入 `activeTasks`、`archivedTasks`、總覽任務統計或 Discord 待辦判斷。這沿用現有資料格式，不需要新增工作表或抓取流程。

替代方案是複製一份新的資料結構或來源；這會讓同一批田野調查資料有兩套生命週期，因此不採用。

### 所有可追蹤任務使用同一套依序勾選規則

移除以 id 白名單判斷 `ld-`、`bh-`、`my-` 的分支。凡進入可追蹤任務清單的群組，勾第 N 項時第 1 至 N 項一起成為草稿，取消第 N 項時第 N 項至最後一起取消。`field-` 群組沒有勾選 UI，因此不套用此規則。

替代方案是繼續增加 id 前綴；新增另一種任務來源時容易再次漏掉，且已與「參考資料／可追蹤任務」的產品區分不一致。

### 以穩定 ID 原子更新手動任務

新增 `updateManualTask(id, input)`。介面接受既有的 `my-` 群組 id，以及與新增相同的名稱、結束時間、任務陣列；既有任務項目同時攜帶其穩定 id。保留的項目沿用 id，即使修正文字或獎勵；新項目取得該群組內未使用的新 id；移除項目的 `taskDone` 鍵在同一個 user lock 中清除。群組 id、建立時間與 `manual:my-…` 屬性鍵保持不變。

更新沿用新增功能的字數、項目數、時間與 9 KB 限制。驗證或寫入失敗時，伺服端舊資料與完成狀態保持原樣，前端編輯表單保持開啟並顯示錯誤。

替代方案是刪除後重建；這會改變群組 id、遺失所有完成紀錄並可能重複 Discord 提醒，因此不採用。

### 重畫任務內容時恢復原本視窗位置

任務頁的勾選、展開收合、放棄、刪除、編輯，以及這些操作的成功或失敗回應，均透過共用的保留捲動重畫流程：重畫前記錄垂直位置，更新 DOM 後在下一個畫面更新時恢復；若新頁面高度不足，接受瀏覽器夾到最大可捲動位置。切換主分頁與按分頁器仍明確捲到頁首。

替代方案是只修補勾選事件；刪除與非同步回應仍會重現同一問題，因此不採用。

### 儲存狀態由任務頁標題列渲染

移除獨立且固定在視窗頂端的 `savebar` 呈現。任務頁標題列左側顯示「任務待辦」，右側顯示未儲存數量與儲存按鈕，說明文字另占一列；窄螢幕維持標題與按鈕在同一列，狀態文字可縮短或換到按鈕前。草稿、一次送出、失敗保留與離頁確認的資料流程不變。

### 總覽沿用任務頁的有效完成狀態

**Supersedes**: task-todo-improvements / 總覽以目前項目的已儲存狀態判斷完成

總覽的任務進度與「快結束了，還沒完成」只計算可追蹤任務，並直接沿用任務頁對目前項目的有效完成狀態（已儲存狀態加上尚未儲存草稿）。只要任務頁把某組判定為 `allDone`，總覽就必須在同一次重畫排除該組，以及來源 URL 相同或去除「限時調查：」前綴後名稱相同的 GO 活動，避免同一活動以「其他」標籤繼續出現在「還沒完成」清單；24 小時內結束的活動統計仍計入該活動。不得對特定任務名稱寫例外。草稿被取消或頁面重新載入後，再依當時有效狀態重算。手動編輯新增項目會使群組重新成為未完成；移除項目的舊完成鍵由伺服端清理。

## Implementation Contract

- **可觀察行為**：任務待辦先顯示「日常田野調查獎勵」參考區，每列只有任務文字與獎勵／原文連結；可追蹤任務仍顯示勾選框。手動群組同時有「編輯」與「刪除」。
- **介面與資料形狀**：新增 Apps Script 呼叫 `updateManualTask(id, input)`；`input` 為 `{ name, end, tasks: [{ id?, text, reward }] }`。成功回傳目前使用者的全部手動任務組，與 `addManualTask`、`deleteManualTask` 一致。
- **完成狀態**：保留項目的 `id` 不變；刪除項目同步刪除 `<groupId>#<taskId>`；新增項目不得重用本群組曾保留項目的 id。名稱或結束時間修改不影響任務完成狀態。
- **失敗行為**：非法 group id、非手動群組、過期結束時間、空名稱、空任務、超過既有限制或過大內容均拒絕，且不得部分寫入。前端顯示伺服端錯誤並保留使用者輸入。
- **捲動行為**：勾選、取消、展開、收合、放棄、刪除與編輯前後保持原垂直位置到瀏覽器可容許的最近位置；切換分頁與清單換頁仍回頁首。
- **驗收**：`node --test tests/gas/*.test.js` 覆蓋參考區無勾選框、依序勾選、編輯保留／清理狀態、捲動呼叫、標題列儲存按鈕及總覽完成排除；`python -m unittest` 維持通過。另以 375、768、1280 px 手動確認任務頁標題列與長內容排版。
- **範圍界線**：只修改看板前端、Apps Script 個人資料方法、測試與文件；爬蟲輸出、試算表 schema、Discord 時程與 GitHub Actions 不在範圍內。

## Risks / Trade-offs

- [把 `field-` 從追蹤清單移除會留下舊 `taskDone` 鍵] → 讀取時忽略這些鍵；本變更不做全面 UserProperties 遷移，避免一次重寫使用者狀態。
- [編輯時錯誤重用任務 id 會把完成狀態套錯] → 更新 API 驗證 id 必須屬於原群組且不得重複，新項目只使用未衝突 id。
- [刪除內容後頁面高度縮短，無法維持完全相同座標] → 明確接受瀏覽器夾到最大捲動位置，但禁止回到頁首，除非頁面本身已不足一個視窗高度。
- [總覽與任務頁若各自計算完成狀態，可能再次出現「已完成卻仍提醒」] → 兩個畫面共用同一個衍生群組的 `allDone` 結果，並以具名任務案例做回歸測試。
